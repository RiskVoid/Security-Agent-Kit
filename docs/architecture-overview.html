Security Agent Kit · Architecture overview

How the Security Agent Kit is built

The kit is a self-hosted AI agent for authorised security work: code review and testing of web apps, APIs, AI apps and networks. Two models do the reasoning. Everything they can touch goes through a small set of tool servers, and the controls live in those servers, outside the model.

System

Containers, networks and the ways out

The agent runtime sits on an internal Docker network with no route to the internet or the host. Each way out goes through a service that applies one rule. Scope, approvals and halt are set from the host, where the agent has no access.

egress-proxy

The agent container's only way out. Allowlisted package registries and vulnerability databases, deny by default. Engagement targets are refused.

litellm

Every model call, from the planner and from the worker. It holds the provider keys and the daily spend cap, and checks each call against the engagement's data rules.

web-mcp

Search and fetch for research. Fetch refuses any host in any engagement's scope and any non-public address, and checks again on every redirect.

kali-mcp

The only way to run a tool or send traffic to a target. Policy, tiers, approvals, the sandbox, the firewall and the audit log all live here.

findings-mcp

The planner's only write path: findings through validated operations, and a fixed list of files such as PLAN.md and the executive summary.

intel-mcp

Cached lookups against OSV, NVD, EPSS and CISA KEV, used to rank dependencies and check versions during verification.

Task flow

One task, from prompt to report

The planner decides what to do and hands the hands-on work to the worker, one focused goal at a time. The worker runs tools and reads code. The planner gets a short result back and verifies what the worker found.

Command path

What happens to every command

Whoever sends it, planner or worker, a command goes through the same eight steps in kali-mcp. Two of them are hard boundaries that hold whatever the model does. The others catch mistakes and keep testing at the agreed intensity.

  1. 1

    Halt and window.

    Refused when the engagement is halted or outside its testing window.

    operator decision
  2. 2

    Tier.

    Classified passive, active or intrusive from the programs it runs. Refused above what RULES.md allows.

    guardrail
  3. 3

    Scope precheck.

    Hosts named in the command are checked against the scope, for a readable early refusal.

    guardrail
  4. 4

    Approval.

    An intrusive command returns APPROVAL REQUIRED with an id. After you approve it on the host, the same command runs once.

    operator decision
  5. 5

    Rate cap.

    Rate-limitable tools get the engagement's maximum rate added or capped.

    guardrail
  6. 6

    Sandbox.

    A new mount and pid namespace, the engagement's own unprivileged user and a cleared environment. It sees one engagement folder and the in-scope code, read-only.

    hard boundary
  7. 7

    Firewall and DNS.

    nftables allows that user only in-scope addresses and names resolved by the engagement's own dnsmasq. The kit's services, link-local and cloud metadata addresses and all IPv6 are dropped.

    hard boundary
  8. 8

    Hash and audit.

    Every file the command created or changed is SHA-256 hashed into the audit log with the command, tier, exit code and duration.

    record

What an approval covers

One run of one exact action. It stores a digest of the command text, the SHA-256 of the programs it runs and the input files it names, and the policy revision. It is consumed once, expires after 24 hours, and goes stale when the policy changes.

Where the arguments came from

A target that tells the agent what to run is the classic hijack. Each approval shows whether a host, path or command text came from the scope, the task, the agent, or content the target wrote. Arguments copied from target content are highlighted.

Models

Two models and who sees what

Tool output and client code are most of the tokens and the most sensitive data. They stay with the worker, which runs where you choose. The planner works from summaries.

Data routes are enforced at the gateway

A pre-call hook in LiteLLM works out where each call's route goes (local, Colab, an API, a cloud provider) and which engagements the call is about. If the destination isn't in an engagement's Client data: rule, or the engagement is halted, the call is refused with a 403. An offline engagement can't reach a cloud model, whatever the conversation asks.

Detection can only add restrictions

Engagements are read from the conversation binding, the worker's task header and tool-call arguments. Tool results are never read for this, so content the agent fetched can't add or remove an engagement. Refused or empty planner replies are retried or answered by a fallback model, unless the rules forbid the fallback.

Worker loop

The loop around the worker model

worker-mcp runs a tool-calling loop on a model that may be small and local. Most of its code deals with what goes wrong in long loops.

Contract

delegate_task carries one goal with a contract: done when, stop when, inputs and one coverage cell. finish returns a typed status and candidates with their proof.

Context

The model gets a digest of each tool output: parsed counts and top items for tools the kit reads, otherwise the head and the tail. Older results shrink to one line with the evidence path. The full output is always on disk.

Malformed calls

A tool call that doesn't parse goes back to the model as an error and never runs. ./rvkit doctor --models checks that a worker model makes well-formed calls.

Stalls

Three identical calls, the same error three times, or eight calls without progress in the records (a new observation or a candidate) by default trigger a nudge, then advice from the planner model, then a stop with status stalled. Output that only looks new doesn't count.

Durability

Each tool call is recorded as started before it runs and done after. After a restart, an action that was in flight is flagged for review. On resume the model is told its result is unknown. Nothing is repeated automatically.

Approval waits

A task waiting for an approval pauses without holding a model slot. Once you decide, it continues by itself and the approved action runs exactly once.

Findings

From lead to finding

A model proposes a finding. Checks the model doesn't control decide whether it stands, and a person approves what goes to the client.

What confirming requires

  • A stated verification method, with an evidence file for methods that produce output.
  • Reproduction steps.
  • Every quote in the write-up found in the cited evidence, and every /src file and line pointing at a line that exists.
  • For an oracle, a record that passed with a clean control.
  • Then the validator: a separate model that sees only the finding and its evidence, and whose only job is to disprove it.

What the report proves

  • Each evidence file's current SHA-256 is checked against the audit log. A file changed after it was produced, or not produced by an audited command, is flagged.
  • Each revision freezes its inputs and records the hash of every artifact.
  • Readiness checks keep it a draft until the summary is written, every candidate is triaged and untested coverage cells are accounted for.

Coverage

Coverage is computed from evidence

Before testing a web target, recon_map builds a map from a sandboxed crawl, API paths named in scripts, OpenAPI and GraphQL schemas and unauthenticated probes. Requests to the same method and path template become one entry with a stable id. The coverage matrix crosses those entries with the test classes that apply to each.

Research loop

The engagement remembers, not the model

Each engagement's findings.db keeps the research records next to the findings: what was observed, what was tried, what it showed. The kit selects from them with no model, so a small worker and a summarised planner start from the same facts.

Packet

A worker task bound to a plan item starts from a research packet: the map entries, observations, findings and earlier attempts for its coverage cell, picked by stable ids in a fixed character budget. get_briefing gives the planner the same packet.

Facts

After each tool call the kit's parsers store what they extract as observations with their origin and evidence path. The call ledger points out an earlier equivalent call, and answers an unchanged file read from it.

Experiments

Every task bound to a plan item leaves an experiment: what was tried, under which conditions, the outcome, with evidence hashes. Negative and blocked results are kept too.

Conclusions

Drawn by rule where a check decides (an oracle passed with a clean control), otherwise by one checked summary whose quotes must be in the evidence. A new build marks them stale; a contradiction makes them unresolved.

Queue

Open questions are ranked with the reason for each position, with slots kept for authorization and tenant isolation. It is advisory. A delegation with the same work key (build, cell, method, identity) as live or answered work is refused, naming the holder.

Methods

An oracle-verified finding leaves a method, proposed for sibling routes it hasn't been proven on. Each re-test runs its own negative control. A confirmed sibling becomes an instance of the same finding.

Control plane

Who can change what

The files the agent can see are not the ones that are enforced. Scope, rules, approvals and halt live in a root-only volume that only host tooling writes.

WhereWho can change itWhat it holds
/control volume in kali-mcpOnly rvctl.py, which only ./rvkit and the console runThe active scope and rules as numbered policy revisions, approvals, halt flags, the authoritative audit log, the credential vault
Console, a host process on 127.0.0.1You, with a session tokenNothing of its own. It calls the same validated operations as the CLI
/work/<engagement>/You, sandboxed commands, the worker, findings-mcpThe SCOPE.md and RULES.md you edit, the plan, evidence, findings.db, the report

Scope is compiled, not read

SCOPE.md and RULES.md in the engagement folder take effect only when ./rvkit scope copies them into the control volume and rebuilds the firewall. An agent that edits them changes nothing. A line the policy compiler can't enforce is an error and stops activation.

One set of operations, three actors

The console, the CLI and the agent's tools all change records through the same operations. Every change names its actor (console:, cli: or agent:) and the revision it was based on. An edit based on an older revision is refused as a conflict, not written over.

Design decisions

MCP is the boundary

Every capability is an MCP tool with a narrow interface. The controls live in those servers, so they hold whichever agent or model calls them.

Firewall hard, tiers soft

Network policy built from the scope can't be argued with. Tiers, rate caps and the precheck catch honest mistakes.

Tiers by program name

Classifying arbitrary code by what it might send isn't reliable. Program names are predictable and easy to review. The cost is documented.

Evidence hashed on write

Files are hashed in the same step that produces them, into a log the agent can't write.

Files on the host

Engagements are plain folders of Markdown, SQLite and tool output. You can read, back up and hand them over without the kit.

Pinned, two weeks old

Every image, package and binary is pinned to an exact version that has been public for at least two weeks.

Measurement

How changes are measured

Controls and capability are tested separately. A control either holds or it doesn't. What a model finds varies from run to run, so it is measured with repeated runs and a spread.

Controls: a test per risk

Each risk the kit has to control has a test that fails if the control breaks: a restart during a run, approval reuse, halt, hostile content, cross-engagement access, report integrity. The suites run against the live stack with a scripted model, on every pull request and nightly.

Capability: scored benchmarks

Nine benchmarks on lab targets, including one with planted instructions. Each expected finding is reported as found in k of n runs, with standard errors. A plain agent on the same model, with only the sandbox, is the baseline. Clean runs restrict lookups so the agent can't read a write-up of the target.

The improvement loop

A change to a prompt, tool description, playbook step or error message goes through one round.

  1. 1

    Baseline

    Every benchmark, several times, on the current code.

  2. 2

    Error analysis

    Failures grouped by cause from fixed rules. Read the records, on tuning benchmarks only.

  3. 3

    Propose

    One small change for one cause, naming the records it came from.

  4. 4

    Candidate

    The same benchmarks, the same number of times, on the branch.

  5. 5

    Judge

    Kept, dropped or incomplete. Dropped changes stay on record with their numbers.

A change is kept only when all three hold

  • The cause shrinks on the five tuning benchmarks, by more than one standard error.
  • Strict recall on the four held-out benchmarks doesn't fall beyond what the runs can tell apart.
  • No safety cause has more records per run, on any benchmark.

Tuning and held-out benchmarks are separate sets, so a change is never checked on the failures it was written from.

Limits

Known limits

The kit is built for a consultant who sets the scope, watches the run and approves intrusive steps. It is not a guarantee of containment against a determined agent.

  • Tiers are assigned by program name. A script at the passive tier, or curl at the active tier, can send intrusive traffic to in-scope hosts without approval, unless the engagement sets Strict tiers: on.
  • Redaction is pattern-based. It is a safety net for what the planner sees, and the values stay in the evidence files.
  • The kali-mcp container needs NET_ADMIN and SYS_ADMIN to build the sandbox. An escape to its root would be serious.
  • The held-out check shows that a change did no visible harm. It doesn't prove the change helped elsewhere.

The full list and what counts as a security bug are in SECURITY.md. The detailed reference is docs/architecture.md.
