01 · Executive summary

What we found

This bounded release-acceptance assessment reviewed Ledgerly Laravel 12 source and compared selected behaviors on vulnerable .16 and fixed .17 deployments. The vulnerable deployment matched the supplied source; the fixed deployment was assessed at runtime only. This is a focused acceptance exercise, not a comprehensive security certification.

Three issues were reproduced on the vulnerable build: one High finding for member-to-administrator profile mass assignment, and two Medium findings for cross-tenant invoice/document disclosure and search SQL injection. All are P1 priorities because they threaten tenant permissions or financial-data confidentiality. Duplicate authorization instances were grouped under one root cause.

The fixed build resisted the tested profile role escalation and boolean search payloads. Invoice owner reads succeeded while foreign reads were denied in both API directions and the tested web direction. The fixed foreign-document request returned 403; a successful owner-document download remains unsupported, so the combined authorization retest is partial. Bob's role was restored and separately verified as member on both builds. All cleanup items are complete; seeded account/session retention remains operator-managed.

Coverage has explicit outcomes, including blocked and excluded work. Limitations include unsupported owner downloads, wrong-auth-mode matrix cells, missing runtime route export and PHP Joern support, untested stored-output experiments and broader privilege fields, and bounded dependency/secrets checks. The operator must set client metadata, review these limitations and approve the report before delivery.

04 · Methodology

How we tested

Testing followed the source-assisted Laravel playbook with bounded adaptations of web-app, API-security, code-review, supply-chain and secrets-review checklists in PLAN.md. Scope: /src/rv-bench/rv-laravel-lab, 10.250.0.16:8000 and 10.250.0.17:8000. Policy revision 9124ff4962c8fba1; maximum rate 10/s. Only these lab hosts were tested.

Sequence: static Laravel map and build identity, PHP Semgrep (25 app files), working-tree Gitleaks, OSV composer.lock (112 packages), manual controller/policy/Blade/config review, baseline login/404/tooling/anonymous API requests, console-approved read authorization matrix, individual failure repeats, and approved bounded boolean SQL injection browser experiment. Matrix: 31 pass, 5 FAIL, 24 blocked; blocked cells are not safety results. Bearer accounts on web routes were labeled session-ended by the kit despite later valid identity checks; mode-aware matrices are recommended.

Approvals were host/console decisions. The first browser experiment reproduced vulnerable search SQL injection and fixed invoice denial, then exited with Download is starting at the fixed owner document. Foreign document and later fixed-search steps did not run. A changed continuation was separately proposed for approval. A preliminary script exited with a missing credential environment variable before login or injection; it is not a completed SQL test. No approval bypass or credential export was attempted.

Evidence consists of audited runs, HTTP exchanges, the map, matrix and browser summaries/requests with SHA-256 provenance; worker transcripts are not finding evidence. OSV empty results required an explicit osv-scanner parser after auto-detection selected Semgrep: import I-005 is authoritative for that file. No persistent fixture changes or mail sends occurred; only ephemeral login sessions were created.

Mass assignment privilege escalation via PATCH /api/profile ($request->all())

http://10.250.0.16:8000 (rv-laravel-lab)
Severity

CVSS vector

CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N

Description

The self-profile endpoint mass-assigns untrusted request fields. A valid Acme member (Bob, user 2) sent PATCH /api/profile with only {"role":"admin"} on vulnerable .16. The response and a separate GET /api/me both showed role=admin. The approved restore changed it back to member.

On fixed .17 the identical approved request returned role=member; a separate read confirmed it stayed member. The tested role-escalation allegation is rejected for the fixed build. Tenant reassignment, password changes and platform-admin escalation were not tested and are not claimed.

Impact

A member can promote their own account to tenant administrator. The supplied InvoicePolicy permits administrators to update tenant invoices, putting financial-record integrity and tenant-admin access at risk. No invoice mutations or administrator actions were performed.

Steps to reproduce
  • As bob-api, GET /api/me; verify user 2, role member, organization 1.
  • With console approval, PATCH /api/profile with Content-Type application/json and body {"role":"admin"}.
  • GET /api/me separately; on .16 role is admin; on .17 it remains member.
  • With separate approval, PATCH {"role":"member"} and verify restoration.
Remediation

Allow-list validated self-service fields (such as name and timezone) using a Form Request and update($request->validated()). Never accept role, organization_id or is_platform_admin from self-profile input. Protect privilege changes with separate administrator-authorized operations and regression tests.

F-001medium · CWE-862Open

Missing tenant authorization exposes invoices and documents

http://10.250.0.16:8000 (rv-laravel-lab)
Severity

Description

Authenticated users on vulnerable .16 can read another tenant's invoices through web/API routes and download its documents. Global object binding is followed by missing tenant policy checks. Alice received Globex invoice 3 and document 2 with confidential fixture markers; the approved matrix also reproduced reverse-direction API access as Carol. Anonymous requests were denied.

Fixed .17 retest: API owner reads succeed and foreign reads return 404 in both directions. Valid Acme web login permits invoice 1 and denies invoice 3 (404) and foreign document 2 (403). The tested foreign-read allegations are rejected for the fixed build. However, a successful fixed owner-document download is still unavailable due browser download limitations; the document retest remains partial, not a complete safety claim. Fixed source was not supplied.

Impact

A legitimate customer account can disclose another customer's invoice amounts, customer details, confidential notes and contract contents. Integrity/availability effects were not tested.

Steps to reproduce
  • Use valid Alice Acme API identity: GET /api/invoices/3 with Accept: application/json on .16; 200 includes GLOBEX-CONFIDENTIAL-2001.
  • Use valid Alice web identity: GET /invoices/3 and /documents/2/download on .16; 200 includes Globex confidential markers.
  • Compare approved owner, foreign tenant and anonymous controls in ledgerly-read-acceptance matrix.
  • Repeat API invoice 3 on .17 as Alice: 404; owner Carol gets its marker in matrix.
Remediation
  • Enforce InvoicePolicy::view and DocumentPolicy::download on every corresponding route/controller.
  • Apply tenant-scoped route model binding or an equivalent global tenant scope with explicit authorization.
  • Add regression tests for both directions, member roles and anonymous access; retain successful owner controls.

F-003medium · CWE-89Resolved

Search SQL injection bypasses the tenant filter

http://10.250.0.16:8000/search?q=
Severity
Medium

CVSS vector

CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N

Description

SearchController reads q and interpolates it into DB::select at lines 13–14 (CWE-89, WSTG-INPV-05). In the approved experiment, Alice's normal no-match query returned no results; OR 1=1 returned all three seeded invoice summaries including GLOBEX-INV-2001; OR 1=0 returned none.

Fixed .17 is NOT affected by these tested payloads: separately approved continuation established valid Acme dashboard session and all three queries returned empty results. This SQL-injection allegation is rejected for the fixed build for the tested cases. Fixed source was unavailable; no broader clean-build assertion.

SQL construction is a distinct root cause from missing object authorization.

Impact

A tenant account can alter SQL predicates to retrieve another tenant's invoice identifiers and customer names. Only the seeded invoice query was used; arbitrary tables, writes and availability effects were not tested.

Steps to reproduce
  • Authenticate as Alice on .16 and verify Acme dashboard.
  • GET /search?q=RV-NO-MATCH-ACCEPTANCE: results [].
  • Send URL-encoded q=RV-NO-MATCH-ACCEPTANCE%' OR 1=1 -- : results include GLOBEX-INV-2001 and Hank Scorpio.
  • q=RV-NO-MATCH-ACCEPTANCE%' OR 1=0 -- returns [].
  • Review the approved browser run evidence for the exact URLs and responses.
Remediation

Use bound parameters or Eloquent instead of SQL interpolation:

1$rows = DB::select(
2    'select id, number, customer from invoices where organization_id = ? and customer like ?',
3    [$request->user()->organization_id, '%' . $q . '%']
4);

Keep tenant filtering server-controlled and add regression tests for quotes, boolean payloads and cross-tenant markers.
